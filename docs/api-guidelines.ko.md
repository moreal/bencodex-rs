# Rust API 가이드라인 평가

[English](api-guidelines.md) · [변경 기록 작성 안내](changelog.ko.md)

2026년 10월 18일, 공식 [Rust API Guidelines 체크리스트](https://rust-lang.github.io/api-guidelines/checklist.html)를 기준으로 공개 API를 검토했습니다. 특히 [다른 라이브러리와의 연동](https://rust-lang.github.io/api-guidelines/interoperability.html), [문서화](https://rust-lang.github.io/api-guidelines/documentation.html), [유연성](https://rust-lang.github.io/api-guidelines/flexibility.html), [향후 변경에 대한 대비](https://rust-lang.github.io/api-guidelines/future-proofing.html)를 살펴봤습니다.

이번 개선의 목적은 **다른 Rust 프로그램에서 이 라이브러리를 자연스럽고 안전하게 사용할 수 있도록 만드는 것**입니다. 가이드라인은 API의 성격에 따라 적용 여부를 판단하는 설계 권고입니다. 이 문서는 개선한 항목, 이미 충족하고 있던 항목, 의도적으로 유지한 예외와 남은 과제를 구분합니다.

팀은 값과 자료형 변환, 인코딩과 입출력, JSON, SIMD를 나누어 검토했습니다. 이후 일반 디코더, 라이브러리 문서, 패키지 정보까지 결과를 통합하고 독립적인 코드 리뷰를 진행했습니다. 기능 플래그로 켜고 끄는 항목을 포함해 공개 라이브러리 API 전체를 검토했으며, CLI나 Bencodex 형식 자체를 재설계하지는 않았습니다.

## 문서를 읽기 위한 용어

| 용어 | 뜻 |
| --- | --- |
| 공개 API | 다른 프로그램에서 호출하거나 구현할 수 있도록 제공하는 함수, 자료형, 트레이트 등을 뜻합니다. |
| 크레이트(crate) | Rust에서 라이브러리나 실행 프로그램을 구성하는 코드 단위입니다. 여기서는 주로 이 라이브러리를 가리킵니다. |
| 트레이트(trait) | 자료형이 제공하는 동작을 나타내는 공통 인터페이스입니다. 예를 들어 `Eq`는 동등성 비교, `Hash`는 해시 계산을 지원합니다. |
| 소유와 빌림 | 데이터를 직접 관리하면 소유한 것이고, 다른 곳에서 관리하는 데이터를 참조해 사용하면 빌린 것입니다. 빌린 데이터는 원본보다 오래 사용할 수 없습니다. |
| `std`와 `no_std` | `std`는 Rust 표준 라이브러리를 사용하는 구성입니다. `no_std`는 표준 라이브러리 없이 사용하는 구성으로, 임베디드 환경 등에 쓰입니다. 이 라이브러리는 `no_std`에서도 동적 메모리 할당이 필요합니다. |
| SIMD | CPU 명령 하나로 여러 데이터를 함께 처리하는 방식입니다. 이 라이브러리에서는 입력을 빠르게 탐색하는 데 사용합니다. |
| 정규형(canonical form) | 같은 값을 표현하는 여러 방식 중 규격이 정한 표준 표현입니다. 값을 읽어 낼 수 있다는 것과 입력이 정규형인지 검증하는 것은 별개의 문제입니다. |

## 발견한 문제와 개선 내용

### 1. Rust의 기본 자료구조와 함께 사용하기 쉽게 개선

관련 항목: **C-COMMON-TRAITS, C-DEBUG**

기존에는 Bencodex 값에 `Eq`와 `Hash`가 없고, 키에는 `Hash`가 없었습니다. JSON 인코딩 옵션에도 디버깅과 비교에 필요한 트레이트가 부족했습니다.

각 자료형의 의미에 맞는 구현을 추가했습니다. 이제 원본을 빌린 데이터와 직접 소유한 데이터도 내용이 같으면 동일하게 비교되고 같은 해시 값을 만듭니다. 바이너리와 텍스트는 바이트 내용이 같더라도 서로 다른 종류로 취급합니다.

### 2. 값을 만드는 표준 변환 보강

관련 항목: **C-CONV-TRAITS, C-CONV**

큰 정수, 포인터 크기의 정수, `BigInt`를 Bencodex 값으로 바꾸는 변환과 키를 값으로 바꾸는 직접 변환이 부족했습니다.

값의 손실이 없는 `From` 구현을 추가했습니다. 소유한 데이터는 변환할 때 그대로 넘기므로 불필요한 복사를 피합니다. 기존 `into_owned`는 데이터를 소유한 값으로 바꾸는 동작이므로 Rust의 이름 규칙에 맞습니다.

### 3. 애플리케이션에서 오류를 다루기 쉽게 개선

관련 항목: **C-GOOD-ERR**

JSON 오류는 일반적인 애플리케이션 오류로 전달하기 어려웠고, 일반 디코더의 오류 메시지는 내부 디버깅 표현을 그대로 출력했습니다.

JSON 오류에 `Display`와 `Error`를 구현했습니다. 일반 디코더의 메시지는 잘못된 입력이거나 예상하지 못한 바이트가 나왔다는 사실과 해당 위치를 설명하도록 바꿨습니다. 기존 오류 종류는 유지했습니다.

### 4. 이미 가지고 있는 데이터와 출력 대상을 유연하게 사용

관련 항목: **C-RW-VALUE, C-GENERIC**

기존 인코딩 API는 문자열이나 벡터를 직접 소유하는 자료형 위주였고, 출력 대상을 가변 참조로 받았습니다.

빌린 데이터에도 `Encode`를 구현하고 `to_writer(W, &T)`를 추가했습니다. 출력 대상을 직접 넘기거나, 계속 사용하려는 출력 대상을 가변 참조로 넘길 수 있습니다. `&mut dyn Write`처럼 구체적인 출력 대상의 종류를 감춘 형태도 지원합니다. 표준 라이브러리를 사용하는 구성과 동적 메모리 할당만 사용하는 구성에서 모두 동작합니다.

### 5. 복사와 메모리 할당 시점을 문서화

관련 항목: **C-CALLER-CONTROL**

기존 문서만으로는 어느 데이터가 원본을 빌리고 어느 데이터가 새 메모리를 할당하는지 파악하기 어려웠습니다.

문자열과 바이너리 데이터의 빌림, 리스트·딕셔너리·큰 정수의 메모리 할당, 소유권을 넘기는 변환, 원본에서 독립된 값을 반환하는 디코딩을 설명했습니다. 호출자가 자신의 용도에 맞춰 복사 시점을 선택할 수 있도록 했습니다.

### 6. SIMD 내부 구현을 공개 API에서 분리

관련 항목: **C-HIDDEN, C-STRUCT-PRIVATE, C-NEWTYPE-HIDE**

기존에는 CPU별 구현, 입력 위치를 저장하는 구조 인덱스, 내부 파서까지 공개되어 있었습니다. 외부 코드가 이런 구현에 의존하면 내부 최적화만 바꿔도 호환성 문제가 생깁니다.

내부 모듈을 비공개로 바꿨습니다. 사용자가 호출하는 기존 두 `decode_simd` 경로는 유지합니다. 구조 인덱스는 완전히 내부에서만 사용하므로, 외부에 제공하기 위한 별도의 래퍼 자료형은 필요하지 않습니다.

이 변경은 내부 모듈을 직접 사용하던 코드에 영향을 줍니다. 대신 `bencodex::simd::decode_simd` 또는 `bencodex::codec::simd::decode_simd`를 사용하세요. 두 함수의 매개변수와 반환형은 유지했습니다.

### 7. 처음 사용하는 사람을 위한 문서와 예제 보강

관련 항목: **C-CRATE-DOC, C-EXAMPLE, C-QUESTION-MARK, C-LINK**

라이브러리 전체를 소개하는 문서가 없고, 일부 예제는 오류를 무시하거나 실행 검증에서 제외되어 있었습니다.

개요, 기능 플래그, 소유와 빌림에 대한 안내와 관련 링크를 추가했습니다. 예제는 `?`로 오류를 전달하고 실제로 실행해 검증하도록 정리했습니다. 외부에서 접근할 수 있는 공개 항목에도 설명을 보강했습니다.

### 8. 실패했을 때의 동작을 명확하게 설명

관련 항목: **C-FAILURE**

인코딩 도중 실패하면 이미 출력된 데이터가 어떻게 되는지, 디코딩은 어떤 경우 실패하는지 설명이 부족했습니다.

오류 조건을 별도 절로 설명하고, 인코딩 실패 시 일부 데이터가 이미 출력되었을 수 있다는 점과 출력 버퍼를 자동으로 비우지 않는다는 점을 명시했습니다. 첫 번째 값만 읽는 동작과 정규형 검증의 한계도 설명했습니다. CPU별 내부 `unsafe` 함수에는 안전하게 호출하기 위한 조건을 기록했습니다.

### 9. 잘못된 입력으로 인한 패닉과 데이터 덮어쓰기 수정

관련 항목: **C-VALIDATE**

딕셔너리에 같은 키가 두 번 나오면 일반 디코더는 패닉이 발생했고, SIMD 디코더는 앞의 값을 덮어썼습니다. 문자열 길이가 지나치게 크면 길이 계산이 넘치는 오버플로도 발생했습니다.

문제를 재현하는 회귀 테스트를 먼저 작성한 뒤 수정했습니다. 이제 두 디코더 모두 중복 키를 오류로 처리하고, 문자열 데이터를 잘라 읽기 전에 범위를 확인합니다.

### 10. 패키지 정보와 최소 Rust 버전 정리

관련 항목: **C-METADATA**

패키지 분류와 정확한 최소 컴파일러 버전이 없고, 홈페이지 주소는 저장소 주소와 중복되어 있었습니다.

분류를 추가하고 최소 지원 Rust 버전을 **1.88**로 명시했습니다. 중복된 홈페이지 설정은 제거했습니다. 호스팅되는 API 문서에서도 JSON과 SIMD 기능을 볼 수 있도록 설정했습니다.

### 11. Sacho로 변경 기록 관리

관련 항목: **C-RELNOTES**

라이브러리 자체의 변경 기록이나 기존 사용자를 위한 수정 안내가 없었습니다.

[Sacho](https://sacho.dev/)를 도입해 변경별 설명을 `changes.d/`에 작성하고, 이를 `CHANGES.md`에 자동으로 모으도록 했습니다. README와 라이브러리 문서는 이 결과물을 가리킵니다. 원본 메모와 생성된 내용의 일치 여부는 CI에서 확인합니다. 작성 방법은 [변경 기록 작성 안내](changelog.ko.md)에 있습니다. 과거 릴리스의 Git 태그를 정비하는 작업은 이번 변경에 포함하지 않았습니다.

### 추가 개선: `no_std`에서 외부 구현이 가능한 입출력 API

`io` 모듈을 공개해, 외부 프로그램에서 `Encode`와 출력 대상인 작성기(writer)를 구현할 때 필요한 자료형을 이름으로 참조할 수 있도록 했습니다.

`std`를 사용하면 표준 입출력 자료형을 그대로 다시 공개합니다. `std`가 없으면 동적 메모리 할당 환경에서 사용할 최소 작성기 인터페이스와, 원인이나 오류 종류 같은 세부 정보를 담지 않는 오류 자료형을 제공합니다. 이 변경은 체크리스트의 특정 항목 외에도 실제 API 사용성을 개선합니다.

## 이미 충족하고 있던 항목과 적용 여부

| 항목 | 평가 |
| --- | --- |
| 이름 규칙: C-CASE, C-GETTER, C-ITER, C-ITER-TY, C-WORD-ORDER | 공개 이름은 Rust의 대소문자와 변환 이름 규칙을 따릅니다. 컬렉션은 `Vec`와 `BTreeMap`의 별칭이므로 순회·조회 관련 이름도 표준 자료형의 규칙을 따릅니다. 별도의 반복자 자료형은 공개하지 않습니다. |
| 컬렉션: C-COLLECT | `BencodexList`와 `BencodexDictionary`는 표준 컬렉션의 `FromIterator`, `Extend`, 순회 기능을 그대로 사용합니다. |
| 스레드 간 사용: C-SEND-SYNC | 공개 데이터, 오류, 옵션은 스레드 간 사용이 가능한 구성 요소를 사용하므로 자동으로 `Send`와 `Sync`를 지원합니다. 내부의 공유 가변 상태를 외부에 노출하지 않습니다. |
| 숫자 출력 형식: C-NUM-FMT | 별도의 이진 숫자 래퍼를 정의하지 않습니다. 임의 정밀도 정수에는 `num_bigint::BigInt`를 사용합니다. 바이너리·텍스트 데이터를 담는 값에 숫자 출력 형식 권고를 적용할 필요는 없습니다. |
| 매크로: C-EVOCATIVE, C-MACRO-ATTR, C-ANYWHERE, C-MACRO-VIS, C-MACRO-TY | 공개 매크로가 없습니다. 변환 구현을 생성하는 내부 매크로는 공개 API가 아닙니다. |
| 예측 가능한 동작: C-SMART-PTR, C-CONV-SPECIFIC, C-METHOD, C-NO-OUT, C-OVERLOAD, C-DEREF, C-CTOR | 변환은 관련 값·키 자료형에 구현되어 있습니다. 사용자 정의 스마트 포인터, 역참조 변환, 연산자 재정의, 계산 결과를 돌려주기 위한 출력 매개변수를 추가하지 않습니다. 작성기 인자는 데이터를 순서대로 내보내는 대상입니다. 표준 자료형의 별칭이나 열거형 값에 별도의 생성자 래퍼는 필요하지 않습니다. |
| 자료형으로 의미 구분: C-NEWTYPE, C-CUSTOM-TYPE, C-BITFLAG, C-BUILDER | 값·키의 종류와 `BinaryEncoding`으로 의미를 구분합니다. 새 래퍼 자료형, 비트 플래그, 빌더가 필요한 불리언 모드 선택이나 플래그 집합, 복잡한 생성 과정은 없습니다. |
| 자원 정리: C-DTOR-FAIL, C-DTOR-BLOCK | 사용자 정의 소멸자가 없습니다. 인코딩이 출력 대상의 버퍼를 암묵적으로 비우지도 않습니다. |
| 디버깅 정보: C-DEBUG-NONEMPTY | 공개 데이터·옵션·오류의 디버깅 출력에는 종류, 내용, 필드 등의 정보가 포함됩니다. `no_std`용 오류의 디버깅 출력에도 자료형 이름이 포함됩니다. |
| 향후 변경 대비: C-STRUCT-BOUNDS, C-SEALED | 데이터 선언에 불필요하게 중복된 제네릭 제약을 추가하지 않습니다. `Encode`, `Decode`, `no_std`용 `Write`는 외부 구현을 위한 확장 지점이므로, 외부에서 구현하지 못하도록 봉인하면 본래 목적에 어긋납니다. |
| 의존성과 라이선스: C-STABLE, C-PERMISSIVE | 이 크레이트와 직접 의존성은 허용적인 라이선스를 사용합니다. 현재 크레이트와 공개 API에 등장하는 `num-bigint`는 모두 1.0 이전 버전입니다. 공개 의존성을 안정 버전으로 유지하라는 권고는 향후 안정 버전 릴리스 시 고려할 사항입니다. |

## 의도적으로 유지한 예외와 남은 과제

### Serde 직접 지원 — C-SERDE

공개 값·키 자료형은 `Serialize`와 `Deserialize`를 직접 구현하지 않습니다. 선택 기능인 JSON API가 내부 Serde 어댑터를 통해 Bencodex JSON 표현을 처리합니다.

일반적인 Serde 지원을 추가하려면 직렬화 형식과 데이터 빌림 규칙을 별도로 설계해야 합니다. 단순히 자동 구현을 추가하면 기존 형식과 다른 표현이 만들어질 수 있습니다.

### 트레이트 객체 사용 — C-OBJECT

`Encode`는 작성기를 제네릭으로 받는 기존 메서드를 유지하므로 `dyn Encode` 형태로 사용할 수 없습니다. 종류가 다른 Bencodex 값을 함께 다룰 때는 공개 값 열거형을 사용할 수 있고, `to_writer`는 작성기 트레이트 객체를 받습니다.

`Decode`는 구현한 값을 소비하므로 구체적인 자료형을 감춘 디코딩 인터페이스로 사용하기에도 적합하지 않습니다. 이번 작업에서는 호출 방식을 재설계하지 않았습니다.

### 공개 옵션 필드 — C-STRUCT-PRIVATE

`JsonEncodeOptions::binary_encoding`은 공개 상태로 유지합니다. 필드가 하나인 단순한 설정이며, 비공개 필드나 빌더로 보호해야 할 특별한 제약이 없습니다. 다만 앞으로 필드를 추가할 때는 기존 코드와의 호환성을 고려해야 합니다.

### 기능 플래그 — C-FEATURE

`std`, `alloc`, `json`, `json-cli`, `simd`는 제공하는 기능을 나타냅니다. 기존 `test`는 선택 의존성을 켜는 과거의 스위치이고, `alloc`은 호환성을 위해 남겨 둔 플래그입니다. `alloc`을 꺼도 이 라이브러리는 동적 메모리 할당이 필요합니다.

이번에는 플래그를 제거하거나 이전하는 대신 실제 동작을 문서에 설명했습니다.

### `u8` 변환 — C-CONV-TRAITS

`From<u8>`를 추가하면 바이너리를 만드는 `From<Vec<u8>>`와 리스트를 만드는 일반적인 `From<Vec<T>>` 구현이 겹칩니다. 기존 바이너리·리스트 변환의 의미를 유지했습니다.

바이트 하나를 숫자로 변환하려면 숫자 종류를 명시적으로 선택하거나, 더 넓은 정수 자료형으로 바꾼 뒤 변환해야 합니다.

### 읽은 길이, 엄격한 검증, 자원 제한 — C-INTERMEDIATE / C-VALIDATE

현재 디코더에는 다음 한계가 있습니다.

- 첫 번째 값만 읽고, 어디까지 읽었는지 호출자에게 반환하지 않습니다.
- 첫 번째 값 뒤의 바이트를 무시하고, 일부 비정규 표현도 허용합니다.
- 중첩된 값은 재귀적으로 읽으며, 설정 가능한 자원 사용 제한이 없습니다.
- SIMD 구조 인덱스가 32비트 위치를 사용하므로 `u32::MAX`바이트보다 큰 입력은 지원하지 않습니다.

읽은 길이를 반환하거나 정규형을 엄격하게 검증하는 API는 별도 추가 과제입니다. 따라서 **디코딩에 성공했다고 해서 입력 전체가 정규형이라고 보장되지는 않습니다.**

## 검증

외부 사용자의 관점에서 다음 동작을 테스트했습니다.

- 데이터를 빌렸는지 소유했는지에 따른 해시와 변환 동작
- 외부 프로그램의 작성기·인코더 구현과 빌린 입력의 인코딩
- 일부만 출력한 뒤 발생하는 오류와 작성기 트레이트 객체 사용
- 애플리케이션으로의 오류 전달과 JSON 옵션
- 중복 키와 문자열 길이 오버플로 처리

기존 규격 예제 데이터와 기능별 속성 기반 테스트도 유지했습니다. 속성 기반 테스트는 다양한 입력을 생성해 지켜야 할 성질을 확인하는 방식입니다. Rustdoc의 사용 예제도 실행해 확인했습니다.

CI에서는 전체 기능 및 `no_std` 구성의 빌드·테스트, 코드 형식, Clippy, 문서 경고, 최소 지원 Rust 1.88을 확인합니다. 로컬 검증은 저장소에 지정된 Rust 1.92를 중심으로 진행했고 Rust 1.88도 확인했습니다.

SIMD의 실제 실행은 AArch64 환경에서 검증했습니다. 다른 아키텍처의 실행 검증은 CI가 담당합니다. 호환성에 영향을 주는 변경과 코드 수정 방법은 Sacho가 모아 주는 [변경 기록](../CHANGES.md)에 있습니다.

아래 표는 **해당 개선 작업 당시의 로컬 검증 결과**입니다. 한국어 번역 과정에서 테스트를 새로 실행했다는 뜻은 아닙니다.

| `cargo test --all-features --locked --offline` | Rustdoc 예제 33개를 포함해 테스트 134개 통과 |

서로 다른 구성의 테스트에는 공통 항목이 있으므로, 위 숫자를 모두 서로 다른 테스트의 개수로 합산하지는 않습니다.

독립적인 리뷰에서 추가 수정이 필요한 정확성 문제는 발견되지 않았습니다. 삭제된 SIMD 내부 모듈이 문서의 구조도에 남아 있다는 지적은 수정했고, 이후 문서를 다시 검토했습니다.
